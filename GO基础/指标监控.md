# 指标监控

## 一、什么是指标监控

日志（Logging）是离散事件，用来排查**单次故障**；

 链路追踪（Tracing）看单次请求完整调用链； 

**指标 Metrics** 是随时间采样的数值，用来看系统**宏观趋势、水位、异常波动**，适合告警、大盘、长期观测。

> 日志：发生了什么；Trace：这一次请求怎么走的；指标：系统整体好不好。

Prometheus 是云原生最主流的时序指标数据库，Go 生态原生支持，也是后端服务监控标配。

## 二、Prometheus四种核心指标类型

| 类型      | 特性                                                         | 适用场景                   | 例子                                               |
| --------- | ------------------------------------------------------------ | -------------------------- | -------------------------------------------------- |
| Counter   | **只增不减，只能加不能减；重启归零**                         | 计数类，总量统计           | 请求总次数、错误总数、抛出异常数                   |
| Gauge     | **可增可减，可直接设置数值**                                 | 当前瞬时状态               | 当前内存占用、在线连接数、goroutine 数量、队列长度 |
| Histogram | 统计**值分布**，预先定义桶 (bucket)，统计落在每个区间样本数量 | 延迟、响应大小这类分布数据 | HTTP 请求耗时分布                                  |
| Summary   | 直接计算分位数（P95/P99），在**客户端本地计算分位数**        | 延迟分位数                 | P99 请求延迟                                       |

Histogram vs Summary 关键区别

- Histogram：服务端算分位数，桶在客户端定义；支持聚合（多实例求和），推荐用在服务监控。缺点：桶划分不合适时精度差。
- Summary：客户端预先算好分位数，**不能跨实例聚合**。适合单实例统计，微服务大盘一般优先 Histogram。

## 三、Go 集成 Prometheus 完整代码解析

```go
package main

import (
	"net/http"
	"time"

	"github.com/prometheus/client_golang/prometheus"
	"github.com/prometheus/client_golang/prometheus/promauto"
	"github.com/prometheus/client_golang/prometheus/promhttp"
)

// 定义指标，使用 Vec 多标签版本（推荐！标签用来区分接口、请求方法、状态码）
var (
	// CounterVec：带标签的计数器
	httpRequestsTotal = promauto.NewCounterVec(
		prometheus.CounterOpts{
			Name: "http_requests_total",
			Help: "Total number of HTTP requests received",
		},
		[]string{"method", "path", "status"}, // 标签维度
	)

	// HistogramVec：带标签直方图，统计请求耗时
	httpRequestDuration = promauto.NewHistogramVec(
		prometheus.HistogramOpts{
			Name:    "http_request_duration_seconds",
			Help:    "Histogram of HTTP request latency in seconds",
			Buckets: prometheus.DefBuckets, // 默认桶：0.005,0.01,0.025,0.05,0.1,0.25,0.5,1,2.5,5,10
		},
		[]string{"method", "path"},
	)
)

// 业务 handler，埋点
func helloHandler(w http.ResponseWriter, r *http.Request) {
	start := time.Now()
	// 业务逻辑
	w.Write([]byte("hello metrics"))
	// 记录耗时
	duration := time.Since(start).Seconds()
	httpRequestDuration.WithLabelValues(r.Method, r.URL.Path).Observe(duration)
	httpRequestsTotal.WithLabelValues(r.Method, r.URL.Path, "200").Inc()
}

func main() {
	http.HandleFunc("/hello", helloHandler)
	// 暴露prometheus指标端点 /metrics
	http.Handle("/metrics", promhttp.Handler())
	http.ListenAndServe(":8080", nil)
}
```

### 关键点说明

1. `promauto.NewXXX` 等价于手动 `prometheus.NewXXX` + `MustRegister`，自动注册指标，代码更简洁；
2. **标签（Label）**：维度拆分，`method/path/status`，方便按接口、请求方法筛选指标；标签不要开太多高基数标签（比如 userId），会爆炸占用存储；
3. `/metrics`：Prometheus 通过拉取（pull）这个 HTTP 接口采集指标；
4. `Inc()`：Counter 增加 1；`Observe()`：Histogram 录入一个样本值。

> Prometheus 是 Pull 模型：Prometheus 主动来服务拉指标，不是服务推送指标。

## 四、RED 监控方法论（微服务标准监控模型）

RED 是 Google 提出，针对**服务里每个接口**的 4 个黄金指标：Rate、Errors、Duration。

> 适用：HTTP/RPC 这类请求型服务，是后端最常用监控方案。

| RED      | 含义                       | PromQL                                                       | 说明                                                         |
| -------- | -------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| Rate     | 请求速率（每秒请求数 QPS） | `rate(http_requests_total[5m])`                              | `rate` 计算时间窗口内每秒增长量，Counter 必须用 rate，不能直接用 raw 指标；[5m] 是时间窗口 |
| Errors   | 错误速率 / 错误率          | 错误 QPS：`rate(http_requests_total{status=~"5.."}[5m])`错误率：`rate(http_requests_total{status=~"5.."}[5m]) / rate(http_requests_total[5m])` | `status=~"5.."` 正则匹配 5xx 服务端错误；可以额外增加 4xx 业务错误 |
| Duration | 请求延迟分布，P99/P95      | `histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m]))` | histogram_quantile 根据 bucket 计算分位数；0.99 = P99 延迟   |

> 补充：还有一个配套黄金指标 Saturation（饱和度），也就是资源水位，属于 USE 方法：CPU、内存、连接数、队列长度（Gauge 类型）。
>
> - RED：面向**服务请求**；USE：面向**底层资源**，两者搭配使用。

## 五、PromQL 语法小要点

1. `rate()`：只用于 Counter，计算每秒增量；`increase()` 是窗口内总增量；
2. 标签过滤 `{label="value"}`，正则 `{label=~"regex"}`；
3. `histogram_quantile`：只能作用于 `_bucket` 指标，不能直接作用于原始 histogram；
4. 时间窗口 `[5m]`：采样范围，一般取抓取间隔 2~5 倍。

## 六、指标、日志、Loki、ELK 的关系（对应课程标签）

- **指标 Prometheus**：大盘、告警、趋势，数值型，轻量；缺点：看不到具体请求内容；

- 日志 Loki / ELK

  ：原始文本日志，用来定位问题细节；

  - ELK：Elasticsearch+Logstash+Kibana，全文检索能力强，资源开销大；
  - Loki：Grafana 配套日志系统，不索引日志内容，只索引标签，轻量，常和 Prometheus 配套一起用；

- 最佳实践：**指标告警触发 → 去日志系统查具体错误日志**。指标发现 “系统不对劲”，日志找到 “哪里不对劲”。

## 七、工程上踩坑点

1. Counter 不能 `Set()`，只能 Inc/Add；服务重启数值归零是正常现象，rate 会自动处理；
2. 高基数标签陷阱：不要把用户 ID、订单 ID 放进标签，指标数量会暴涨，Prometheus 存储爆炸；
3. Histogram 的桶选择：如果业务延迟大多集中在 100ms 以内，默认桶粒度太粗，要自定义 Buckets；
4. 指标命名规范：`{namespace}_{subsystem}_{name}_{unit}`，例如 `http_request_duration_seconds`，单位放末尾；
5. 不要埋点过多无关指标，每个埋点都有少量性能开销。

## 八、学习小结

1. Prometheus 四大指标：Counter (计数)、Gauge (瞬时值)、Histogram (分布桶)、Summary (客户端分位数)；
2. Go 使用 client_golang 库，定义指标 + 埋点 + 暴露 `/metrics`；
3. RED 方法论：QPS、错误率、延迟，是接口监控的核心，配合 PromQL 查询；
4. 指标负责告警大盘，日志（Loki/ELK）负责故障细节排查，两者互补。
