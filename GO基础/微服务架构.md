#  微服务架构

**一句话定义**：把一个大应用拆成一组 "独立部署、独立扩展、各自管自己数据" 的小服务，每个服务负责一个业务能力（用户、订单、支付……），服务之间通过网络（HTTP/gRPC 或消息队列）协作。

## 微服务架构总览

先给你一张架构全景图：业务按限界上下文拆成独立服务，每个服务独占数据，横切基础设施负责治理。

```
【调用链：自上而下】
客户端（浏览器 / App / 外部系统）
        │ HTTP / gRPC
        ▼
API 网关：路由 · 鉴权 · 限流 · 协议适配
        │ 统一路由分发
        ▼
┌──────────────── 业务服务层（按限界上下文拆分）────────────────┐
│  User Service       用户上下文                                 │
│  Order Service      订单上下文                                 │
│  Payment Service    支付上下文                                 │
│  Inventory Service  库存上下文                                 │
│  Notification Service 通知上下文                               │
│  （服务之间通过 gRPC / 事件互相调用）                          │
└────────────────────────────────────────────────────────────────┘
        │ 各自独享数据
        ▼
┌──────────────── 数据层（数据按服务隔离，不共享）───────────────┐
│  用户库 │ 订单库 │ 支付库 │ 库存库 │ 通知库                    │
└────────────────────────────────────────────────────────────────┘

【横向基础设施 · 所有服务共享的治理能力】
1. 服务注册与发现：etcd / Consul / Nacos —— 动态上下线、寻址
2. 配置中心：Nacos / Apollo —— 动态配置、多环境隔离
3. 消息队列：Kafka / RocketMQ —— 异步解耦、削峰填谷
4. 分布式事务：TCC / Saga / MQ —— 跨服务最终一致性
5. 可观测性：链路追踪（Jaeger / SkyWalking）、日志（ELK / Loki）、监控（Prometheus + Grafana）
（另：API 网关、熔断/限流/降级 也在治理体系内）
```

## 一、什么时候该拆：默认单体，拆是例外

你笔记里的判断标准是对的，我再补充几条业界常用的判据：

表格

| 触发信号       | 说明                                                         |
| -------------- | ------------------------------------------------------------ |
| 团队规模       | 3 个以上团队在同一代码库频繁冲突；单个服务宜由 6–10 人（"两个披萨团队"）维护 |
| 发布节奏不同   | 一个模块一天发多次，另一个一周发一次，互相阻塞               |
| 资源需求差异大 | 某模块需要百倍于其他模块的扩展资源                           |
| 技术栈异构     | 新能力需要不同运行时（如 Python 做 ML 推理、Go 做高并发网络），无法干净地融入单体 |
| 合规隔离       | 处理 PCI/HIPAA 等敏感数据的模块需要独立审计边界              |

核心观点：**很多成功公司（Shopify、Etsy）都是先单体、后按需抽取服务**，过早拆分是业界公认最昂贵的错误之一。System Design SandboxSystemDesignWasil Zafar

## 二、怎么拆：DDD 限界上下文

你笔记的例子（用户 / 订单 / 支付 / 库存 / 通知）就是标准做法，补充三个要点：

1. **边界判断标准**：问一句 "这个能力能不能独立变化？"—— 如果支付规则的演进不影响订单匹配，它们就属于不同的上下文，应该拆开。Layrs
2. **单一职责 + 数据隔离**：每个服务只做一件事，**各自拥有独立数据库**，在数据层彻底解耦，才能获得独立扩展和独立发布的能力。腾讯云
3. **反例**：按技术分层拆（把 controller/service/dao 各拆成一个服务）是典型错误 —— 这会导致 "分布式单体"，后面第五节展开。

## 三、微服务框架的 "标配"：横向基础设施

这是框架设计的核心。拆完服务只是第一步，真正的工作量在**治理体系**—— 你的课程如果继续往下学，一定会碰到这些组件：

表格

| 能力               | 解决什么问题                         | 常见实现                                              |
| ------------------ | ------------------------------------ | ----------------------------------------------------- |
| 服务注册与发现     | 服务动态上下线、互相寻址             | etcd / Consul / Nacos                                 |
| 配置中心           | 动态配置、多环境隔离                 | Nacos / Apollo                                        |
| API 网关           | 统一入口：路由、鉴权、限流、协议适配 | Kong / APISIX / 自研网关                              |
| 熔断 / 限流 / 降级 | 防止雪崩、保护下游                   | Sentinel / Hystrix                                    |
| 消息队列           | 异步解耦、削峰填谷、事件驱动         | Kafka / RocketMQ                                      |
| 分布式事务         | 跨服务数据一致性                     | 2PC / TCC / Saga / 本地消息表 + MQ                    |
| 可观测性           | 链路追踪、日志聚合、指标监控         | Jaeger / SkyWalking、ELK / Loki、Prometheus + Grafana |

**分布式事务值得单独说**：拆成多个服务后，一个业务操作横跨多个数据库，本地事务失效了。业界方案各有代价：2PC 强一致但性能差、阻塞高；TCC 把资源锁下沉到业务层、侵入性强但一致性好；Saga 把长事务拆成短事务 + 补偿操作，适合订单全流程这类长流程；本地消息表 + MQ 适合异步通知等简单场景。**原则是：能避免跨服务事务就避免 —— 先检查服务边界是不是画错了。**腾讯云Apache Seatasynchronium.github.io

## 五、最容易踩的坑（反模式）

1. **分布式单体**：最大的失败模式 —— 服务物理上拆开了，但共享数据库、逻辑高度耦合，部署一个服务要连带部署一串，等于 "披着微服务外衣的大单体"。所有分布式的成本都付了，解耦的好处一点没拿到。synchronium.github.ioDEV Community
2. **过早 / 过度拆分**：把复杂度从代码转移到了网络和运维，团队小的时候尤其致命。腾讯云开发者社区
3. **低估分布式事务成本**：为本来一个本地事务就能解决的场景，付出了巨大的架构代价。博客园
4. **组织没跟上（康威定律）**：服务边界应与团队结构一致，否则架构和协作互相拧巴。
