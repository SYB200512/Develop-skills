## 一、服务通信的本质

微服务之间是**跨进程、跨网络**通信，这与单体内部的函数调用有本质区别。设计服务通信时，你要同时回答三个问题：

1**.同步还是异步？**--调用方要不要等结果

2.**消息模式是什么？**--请求 - 响应（问答式）还是事件通知（广播式）

3.**可靠性怎么保证？** -- 消息会不会丢、会不会重复、顺序乱不乱

## 二、同步通信：REST vs gRPC

表格

| 维度       | REST                    | gRPC                                                     |
| ---------- | ----------------------- | -------------------------------------------------------- |
| 传输协议   | HTTP/1.1（也可 HTTP/2） | 仅 HTTP/2                                                |
| 数据格式   | JSON（文本、可读）      | Protobuf（二进制）                                       |
| 契约       | 可选（OpenAPI）         | 强制（.proto 文件）                                      |
| 性能       | 一般                    | 优秀（payload 小 3–10 倍，序列化快 10 倍量级）           |
| 流式       | 有限（SSE/WebSocket）   | 原生支持 4 种模式（一元 / 服务端流 / 客户端流 / 双向流） |
| 浏览器支持 | 完整                    | 有限，需要 grpc-web 代理                                 |
| 代码生成   | 可选                    | 内置（多语言）                                           |
| 学习曲线   | 低                      | 中                                                       |

**选型要点**：gRPC 的性能优势来自 "HTTP/2 多路复用 + Protobuf 二进制压缩 + 强类型契约"，第三方基准显示同场景下吞吐可高数倍但**真正决定选谁的不是延迟，而是 "谁在调用你的 API"**—— 对外部 / 浏览器 / 第三方开放用 REST，内部服务之间追求性能与强契约用 gRPC。

## 三、异步通信：Kafka vs RabbitMQ

| 维度     | Kafka                | RabbitMQ                        |
| -------- | -------------------- | ------------------------------- |
| 定位     | 分布式事件流平台     | 通用消息代理                    |
| 吞吐     | 极高                 | 中等                            |
| 延迟     | 毫秒～百毫秒级       | 微秒～毫秒级，更低              |
| 消息保留 | **默认保留，可重放** | 消费后删除                      |
| 典型模式 | 事件流 / 发布订阅    | 任务队列 / 灵活路由（exchange） |

**两种消息模式要分清**：

- **任务队列（Point-to-Point）**：一条消息只被一个消费者处理 —— 适合 "邮件发送、积分计算" 这类任务分发，RabbitMQ 的强项。
- **发布订阅（Pub/Sub）**：一条事件被多个消费者各自消费 —— 订单创建后，通知服务、库存服务、积分服务各取所需，Kafka 的强项。

还要注意：**异步不是 "不用等" 那么简单**。事件驱动里生产者发布事件后立刻返回，消费者稍后处理 —— 这解耦了可用性（消费者不在线也不阻塞），但数据变成 "最终一致"，且要处理消息不丢、不重、不乱序三大难题。

## 四、让异步真正可靠的四个模式

1. **Outbox 模式**：业务数据和事件写进**同一个数据库的同一个事务**（outbox 表），由独立 relay 进程投递到 MQ—— 解决 "数据库改了、消息没发出去" 的双写问题。
2. **幂等消费**：主流 MQ 只保证 at-least-once（至少一次），消息**必然可能重复**，所以消费者必须幂等 —— 用事件 ID 去重或数据库唯一约束，让 "处理两次" 和 "处理一次" 结果相同。
3. **死信队列 DLQ**：消费失败的消息不能无限重试或静默丢弃，进 DLQ 后人工 / 定时补偿。
4. **Saga**：跨服务长事务拆成一系列本地事务 + 补偿操作，失败时按相反顺序回滚（上一轮讲分布式事务时提过）。
