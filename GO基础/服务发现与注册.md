# 服务发现与注册

## 先回答：为什么一定要服务发现？

你写单体时不存在这个问题：所有代码在同一个进程里，直接函数调用。拆成微服务后，服务变成了**多个实例、动态变化**：

- 订单服务要调用用户服务，得知道用户服务的**地址**（IP: 端口）
- 但实例会**随时变化**：扩容加一台、宕机重启换 IP、发布滚动更新……
- 写死 IP？实例一挂 / 一变，请求就全失败

**服务发现解决的就是 "谁在哪、谁还活着" 这个问题。** 它的本质是一个闭环：

## 三种发现模式（你笔记的核心表，展开讲）

**核心区别就一句话：谁负责 "查注册中心 + 选实例"。**

![image-20260919184831384](C:\Users\12472\AppData\Roaming\Typora\typora-user-images\image-20260919184831384.png)

**三种模式对比表：**

| 维度         | 客户端发现                        | 服务端发现              | DNS 发现                  |
| ------------ | --------------------------------- | ----------------------- | ------------------------- |
| 谁查注册中心 | 客户端                            | 负载均衡器              | DNS 服务器                |
| 谁做负载均衡 | 客户端（代码里）                  | LB / 网关               | 轮询或客户端              |
| 代表         | Consul、Eureka+Ribbon             | K8s Service、nginx、ALB | CoreDNS、Consul DNS       |
| 优点         | 无中间一跳、灵活                  | 客户端极简、集中治理    | 零依赖、标准协议          |
| 缺点         | 客户端要 "聪明"、每种语言都要实现 | LB 是瓶颈 / 单点        | 更新慢（TTL）、无健康详情 |
| 典型场景     | 服务间 gRPC 直连                  | 对外 API 网关           | K8s 集群内部              |

**你笔记里的 Consul 示例属于第 ① 种**：客户端自己 `client.Agent().Services()` 拿地址列表，自己在代码里选实例直连。

## 注册中心选型（CAP 视角）

注册中心本身也是分布式系统，绕不开 CAP 取舍：

cp：宁可查不了，不能给错号

ap：宁可给过时的号，不能不查

| 注册中心      | CAP          | 一致性                | 健康检查               | 特点 / 场景                      |
| ------------- | ------------ | --------------------- | ---------------------- | -------------------------------- |
| **Consul**    | CP           | Raft 强一致           | HTTP/TCP/gRPC 主动探活 | 多数据中心强、安全，适合严谨系统 |
| **Nacos**     | AP+CP 可切换 | 临时实例 AP / 持久 CP | 心跳 + 主动探测        | 国内主流，自带配置中心，电商首选 |
| **Eureka**    | AP           | 最终一致              | 客户端心跳             | 经典但已停更，追求可用性         |
| **etcd**      | CP           | Raft                  | 租约 (TTL)             | K8s 在用，K8s 生态首选           |
| **ZooKeeper** | CP           | ZAB                   | 临时节点               | Dubbo 生态经典，运维重           |

博客园CSDN博客腾讯云Nacos

**选型直觉**：K8s 环境 → etcd（K8s 自带）；Java/Spring Cloud → Nacos；Go 自建 → Consul（就是你这门课用的）；要求极高可用性（可用 > 一致）→ AP 系。

## 健康检查：笔记里 `Check` 那段的含义

| 方式         | 谁主动            | 怎么工作                                                 | 代表                |
| ------------ | ----------------- | -------------------------------------------------------- | ------------------- |
| **主动探测** | Consul 主动去访问 | 每 10s 访问 `/health`，返回 200 = 活，超时 / 非 200 = 死 | 你笔记的 HTTP Check |
| **心跳上报** | 服务自己上报      | 服务每 5s 告诉 Consul"我还活着"（续约）；超时没报 = 死   | TTL Check           |

你笔记代码里的 `Check` 是服务发现的**灵魂**—— 它决定 "挂了会不会被摘除"：

```go
Check: &api.AgentServiceCheck{
    HTTP:     "http://localhost:8080/health", // Consul 每 10s 来探一次这个接口
    Interval: "10s",
}
```

三个常用字段（笔记没写全，补上）：腾讯云HashiCorpHashiCorp

- `Timeout`：单次探测超时（如 `5s`）—— 超过算失败

- `DeregisterCriticalServiceAfter`：连续失败多久**自动摘除**（如 `30s`）—— 没有它，死实例会一直占着注册表

- 服务端 `/health` 要返回 **200** 才算健康；返回 503 = 主动宣布 "我扛不住了，别调我"

  

## Go + Consul 完整实践（把笔记代码补成能跑的闭环）

**① 启动 Consul**（你之前已会，一条命令）：

```go
docker run -p 8500:8500 hashicorp/consul
```

**② user-service 启动时注册自己**（写在服务自己的 main.go 里 —— 这正是 "服务自己来登记"）：

```go
package main

import (
    "fmt"
    "net/http"

    "github.com/hashicorp/consul/api"
)

func main() {
    // 1. 连上 Consul（默认就是 localhost:8500）
    client, _ := api.NewClient(api.DefaultConfig())

    // 2. 注册自己 + 登记健康检查
    client.Agent().ServiceRegister(&api.AgentServiceRegistration{
        ID:   "user-service-1",               // 这个实例的编号
        Name: "user-service",                 // 服务名（别人查这个）
        Port: 8080,                           // 我的端口
        Check: &api.AgentServiceCheck{
            HTTP:     "http://localhost:8080/health", // 探我这个地址
            Interval: "10s",                          // 每 10 秒探一次
            DeregisterCriticalServiceAfter: "30s",    // 连续坏 30 秒自动划掉
        },
    })
    fmt.Println("已注册到 Consul")

    // 3. 服务正常启动，提供 /health 和业务接口
    http.HandleFunc("/health", func(w http.ResponseWriter, r *http.Request) {
        fmt.Fprint(w, "ok") // 返回 200 = 我还活着
    })
    http.ListenAndServe(":8080", nil)
}
```

**④ 订单服务查簿子**（调用方代码，注意那个 `true`）：

```go
package main

import (
    "fmt"
    "github.com/hashicorp/consul/api"
)

func main() {
    client, _ := api.NewClient(api.DefaultConfig())

    // 查 user-service 所有【健康的】实例
    entries, _, _ := client.Health().Service("user-service", "", true, nil)
    for _, e := range entries {
        fmt.Printf("活着的实例: %s:%d\n", e.Service.Address, e.Service.Port)
    }
    // 然后随便挑一个地址，发 HTTP 或 gRPC 请求
}
```

**怎么验证跑通了**（三个命令）：

```bash
# ① 看 Consul 上注册了哪些服务（网页）
# 打开 http://localhost:8500/ui

# ② 命令行查：user-service 的所有实例及健康状态
curl localhost:8500/v1/health/service/user-service

# ③ 手动模拟一次探活（就是 Consul 每 10s 干的事）
curl localhost:8080/health   # 返回 ok，200
```

**关键点就一个**：`Health().Service(..., true)` 里的 `true` = **只要健康的**—— 这就是上一格④健康检查的落地。你把 user-service 停掉，30 秒后 Consul 把它划掉，订单服务再查就只有空列表，**请求永远不会打到死服务上**。

## 高频面试题（这一课的考点）

1. **为什么微服务需要服务发现？** 实例动态变化，写死 IP 会失效；需要 "谁在哪、谁活着" 的注册表。
2. **客户端发现和服务端发现区别？** 谁查注册中心、谁做负载均衡（客户端 vs LB）。
3. **服务挂了怎么被摘除？** 健康检查（HTTP/TTL）+ `DeregisterCriticalServiceAfter`。
4. **注册中心选 CP 还是 AP？** 服务发现场景更看重可用性（AP 系更常见），但金融等强一致场景选 CP。
5. **K8s 里怎么做服务发现？** Service + CoreDNS：为服务声明一个 Service，自动获得域名 `服务名.命名空间.svc.cluster.local`，CoreDNS 把它解析到 ClusterIP（虚拟 IP），kube-proxy 再把流量转发给健康的后端 Pod（就绪探针决定谁在列）。
