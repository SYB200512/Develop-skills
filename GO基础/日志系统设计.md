# 日志系统设计

## 一、原因

先理解问题根源：**单体时代**日志写在本地文件，出问题 ssh 上去 `tail -f` 就完事；但到了**微服务 + 容器时代**

- 服务拆成几十上百个实例，日志分散在每台机器、每个容器里；
- 容器一重启日志就丢了；
- 一个用户请求跨 3~5 个服务，报错散落在不同节点，你根本不知道去哪找。

所以日志系统设计要回答 4 个问题：**日志在哪？怎么收？怎么存？怎么查？** 对应的就是一条完整 pipeline：

> **产生 → 采集 → 存储 → 检索 / 可视化**

## 二、结构化日志（slog详解）

### 1.文本日志 vs 结构化日志

| 对比          | 传统文本日志                                    | 结构化日志                                                   |
| ------------- | ----------------------------------------------- | ------------------------------------------------------------ |
| 样子          | `2026-05-26 user 123 logged in, ip 192.168.1.1` | `{"time":"...","level":"INFO","msg":"user login","user_id":"123"}` |
| 机器可解析    | ❌ 要正则猜                                      | ✅ 直接是 JSON /key-value                                     |
| 可检索 / 聚合 | 极难                                            | 按字段精确过滤、聚合                                         |
| 跨字段关联    | 靠人肉                                          | 工具原生支持                                                 |
| 可加索引维度  | 无                                              | `user_id`、`order_id` 直接当字段                             |

**一句话：结构化日志让 "日志" 从给人看，变成 "给机器和工具看"。** 没有结构化，后面的 Loki/ES 全都没法高效工作。

### 2. slog 核心用法

Go 1.21+ 标准库自带 `log/slog`，不需要第三方库：

```go
import "log/slog"

// ① 创建 logger：JSON 输出，级别 Info
logger := slog.New(slog.NewJSONHandler(os.Stdout, &slog.HandlerOptions{
    Level: slog.LevelInfo,
}))

// ② 打一条日志：msg + 一组 key-value 字段
logger.Info("user login",
    "user_id",    "123",
    "ip",         "192.168.1.1",
    "duration_ms", 42,
)
```

输出（真正的 JSON）：

```json
{"time":"2026-05-26T10:00:00Z","level":"INFO","msg":"user login","user_id":"123","ip":"192.168.1.1","duration_ms":42}
```

### 3. 几个关键 API

```go
// 预设字段：With 给所有后续日志带上公共字段（服务名、环境、版本）
logger = logger.With("service", "user-service", "env", "prod")

// 级别：Debug / Info / Warn / Error，按 Level 过滤输出
logger.Debug("开始处理")            // < Info，被 Level:Info 过滤掉
logger.Info("正常路径")
logger.Warn("重试中", "retry", 3)
logger.Error("调用失败", "err", err)

// 属性分组：把相关字段包成一坨，便于组织
logger.Info("user login",
    slog.Group("user", slog.String("id", "123"), slog.String("name", "alice")),
)

// 带来源：HandlerOptions.AddSource 会在日志里加上文件和行号
```

**几个易错点：**

- **不要用 `fmt.Sprintf` 拼字符串进 msg**，那是回到文本日志老路，字段会散失成一行字符串。要用 `logger.Info("msg", "key", value)` 的键值对。
- **日志级别不是装饰**：`LevelInfo` 意味着 Debug 全被丢弃，生产想调细，改 `HandlerOptions.Level` 即可，不用改代码。
- **别打敏感信息**：密码、token、身份证号永远不进日志字段。

### 四、日志设计的最佳实践

| 原则               | 说明                                                         |
| ------------------ | ------------------------------------------------------------ |
| **统一格式**       | 全服务用同一种 slog + 相同字段命名，采集端才好统一解析       |
| **带上关联 ID**    | 每条日志带 `trace_id`/`request_id`，才能和链路追踪对上（呼应上一课） |
| **级别克制**       | 别把 Info 当垃圾桶；关键业务打 Info，异常打 Error，偶发可重试打 Warn |
| **Error 带上下文** | `logger.Error("调用订单服务失败", "err", err, "order_id", id)`，而不是裸 err |
| **落 stdout**      | 打到标准输出（原因见下），而不是写死文件路径                 |

## 三、日志收集架构：逐层拆解

课程给的链路：

```plaintext
App → stdout → Filebeat/Promtail → Loki/Elasticsearch → Grafana/Kibana
```

### 第 1 层：应用层 —— 为什么打 stdout 而不是写文件？

- 容器 / K8s 里 **stdout 是约定**：容器引擎自动接管 stdout/stderr，收集器从那里读，不用侵入应用。
- 写文件有坑：容器重启丢文件、多副本日志互相覆盖、磁盘写满。**打 stdout，让 "日志存哪" 变成基础设施的事，应用只管吐。**
- 所以 slog 用 `os.Stdout` 作为 handler 输出，就是顺应这个约定。

### 第 2 层：采集层 —— Filebeat 还是 Promtail？

两个轻量采集器，常以 **DaemonSet（每个节点一个）或 Sidecar** 方式跑，自动把各容器 stdout 日志读走、转发。

表格

|      | Filebeat                     | Promtail                                  |
| ---- | ---------------------------- | ----------------------------------------- |
| 生态 | Elastic 系（喂给 ES）        | Grafana 系（喂给 Loki）                   |
| 特色 | 成熟稳定、可加工、可多路输出 | 能自动从 K8s 拿**标签**（pod、namespace） |
| 消耗 | 略重                         | 更轻                                      |
| 配置 | filebeat.yml                 | promtail.yml                              |

关键点：**采集层是 "搬运工"，它自己几乎不存数据**，只负责把日志安全地送到存储端。

### 第 3 层：存储层 —— Loki 还是 Elasticsearch？

这是架构分叉的核心，取决于**你要不要全文检索**：

表格

| 维度     | Loki                                                  | Elasticsearch                         |
| -------- | ----------------------------------------------------- | ------------------------------------- |
| 索引策略 | **只索引标签**（服务名、pod、级别），正文不建全文索引 | 全文索引，正文可任意检索              |
| 成本     | 极低，适合海量日志长期存                              | 高（内存 / 磁盘吃紧），日志量大时很贵 |
| 检索能力 | 标签 + LogQL 查询；正文按需加载                       | Lucene 语法，全文全文搜               |
| 查询速度 | 标签过滤快，全文慢                                    | 全文快                                |
| 常搭配   | Grafana                                               | Kibana                                |
| 定位     | **成本优先**，够用就好                                | **检索力优先**，复杂分析              |

**选型直觉：** 如果主要用途是 "按服务 / 级别 / 关键词快速翻最近日志 + 和 Metrics 联动"，**Loki 足够**；如果需要复杂的全文检索、字段级分析、安全合规审计，**Elasticsearch** 更强但要付出成本。

### 第 4 层：可视化层 —— Grafana 还是 Kibana？

- **Grafana**：数据源是 Loki（也可接 Prometheus 等），**一个面板同时看日志 + 指标 + 链路**，这是它最大优势。
- **Kibana**：数据源是 ES，日志分析、可视化、告警一体，ES 生态原生。

> 现实里的常见组合：**Grafana + Loki（轻量、便宜、和 Prometheus/OTel 全家桶打通）** vs **Kibana + ES（重、贵、检索强）**。

## 五、总结

日志系统设计的本质，是把**日志从 "散落在各台机器上的文本" 变成 "集中、可检索、可关联的结构化数据"**。你只要做好两件事：

1. **源头**：用 slog 打结构化 JSON 到 stdout，带 `trace_id`；
2. **架构**：选一条 pipeline —— 轻量就 `Promtail → Loki → Grafana`，要全文检索就 `Filebeat → ES → Kibana`。

## 一个完整案例：用户报 "登录失败"

把上面的方法论走一遍，你就明白日志到底怎么救命了：

**① 发现问题**：产品群里有人喊 "登录失败"，或监控显示 `/login` 错误率上升。

**② 锁定范围**：Grafana 里查今天 `{job="user-service"}` 的日志。

**③ 按级别筛 ERROR**，出来了这条：

```
{"time":"10:00:01","level":"ERROR","msg":"login failed","trace_id":"88e46451","user_id":"123","reason":"invalid password"}
```

**④ 读字段 + 串联**：

- 看到 `reason: invalid password` → 表面是 "密码错"。

- 但你多想一步：

  是不是只有这一个用户？还是所有用户都失败？

  - 查 `|= "invalid password"` 统计，如果**大量用户同时**这样 → 不是用户输错，是**你这边认证逻辑 / 上游服务坏了**。
  - 点开其中一条的 `trace_id: 88e46451`，看到这次请求的完整日志链：入口日志 → 查用户日志 → **DB 查询超时** → 走了错误的失败分支 → 误报 "密码错"。

**⑤ 还原根因**：真正原因不是用户输错，而是**数据库查询超时**，导致认证走了错误分支。修复 DB 连接池配置，补一条 "DB 超时" 的 WARN 日志，下次一眼就能看出来。

> 这就是日志排查的价值：**单看一条 ERROR，你只知道 "错了"；靠 trace_id 把同一次请求串起来，你才知道 "错在哪儿、为什么错、影响谁"**。
