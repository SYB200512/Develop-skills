# 数据库优化

## 一、MySQL 慢查询日志：抓到慢 SQL

慢查询日志作用：**自动记录执行时间超过阈值的 SQL**，用来发现线上慢 SQL。

```sql
-- 开启慢查询日志（全局，重启MySQL失效；生产建议写到my.cnf配置文件）
SET GLOBAL slow_query_log = 'ON';
-- long_query_time=1：执行超过1秒的SQL，会被记录进慢查询日志
SET GLOBAL long_query_time = 1;
```

- 注意：`SET GLOBAL` 是运行时修改，MySQL 重启后配置丢失；生产环境要修改配置文件持久化。
- 日志里面会记录：SQL 语句、执行耗时、扫描行数、时间戳。

**第一步优化流程：慢查询日志捕获慢 SQL → EXPLAIN 分析执行计划 → 加索引 / 改写 SQL 优化**

## 二、EXPLAIN 分析执行计划（核心）

在 SQL 前面加上 `EXPLAIN`，MySQL**不会真正执行 SQL**，而是返回这条 SQL 的执行计划。

```
EXPLAIN SELECT * FROM users WHERE email = 'alice@example.com';
```

### 重点字段讲解

1. **type（最重要！访问类型，优先级从差到好）** `ALL` > `index` > `range` > `ref` > `eq_ref` > `const`

- `ALL`：**全表扫描**，最差。遍历整张表每一行，数据量大的时候极慢，必须优化。
- `index`：索引全扫描，扫描整个索引树，比 ALL 好一点，但依然不好。
- `range`：范围索引扫描，`> < IN BETWEEN`，分页、范围查询常用。
- `ref`：非唯一索引匹配，多个行可以匹配到这个值。
- `eq_ref`：关联查询，主键 / 唯一索引一对一匹配。
- `const`：主键 / 唯一索引等值查询，最多匹配 1 行，最优。

> 优化目标：尽量达到 `ref` / `eq_ref` / `const`，尽量避免 `ALL`。

1. **rows** MySQL 预估**需要扫描多少行**才能找到目标数据。 数字越大越慢。比如你只想要 1 条数据，rows 预估 10000，说明扫描大量无效行。
2. **Extra 额外信息（重点，标记问题）**

- `Using filesort`：**文件排序**。MySQL 无法利用索引完成排序，需要额外内存 / 磁盘排序。`ORDER BY` 没索引最容易出现，性能差。
- `Using temporary`：**创建临时表**，常见于 GROUP BY，开销很大。
- `Using index`：**覆盖索引优秀**，查询需要的数据全部在索引里，不需要回表读取原数据表。
- `Using index condition`：索引条件下推，也是比较好的。

## 三、常见问题、现象、解决方案（表格）

表格

| 问题表现        | EXPLAIN 特征             | 解决方案                                                   |
| --------------- | ------------------------ | ---------------------------------------------------------- |
| 全表扫描        | `type=ALL`               | 给 where 过滤字段建立索引                                  |
| 排序很慢        | Extra: `Using filesort`  | 让 order by 的字段加入索引，利用索引天然有序特性           |
| GROUP BY 性能差 | Extra: `Using temporary` | 给 group by 字段建立合适索引，避免临时表                   |
| 大量回表查询    | 没有 Using index         | 建立**覆盖索引**，查询字段全部放进索引，不用回表查原始数据 |

### 回表 & 覆盖索引简单理解

InnoDB 主键索引是聚簇索引：索引叶子节点存整行数据；二级索引叶子节点存主键 ID。

- 普通二级索引：通过索引找到主键 ID，**再拿 ID 去主键索引读取完整行，这个动作叫回表**。
- 覆盖索引：索引里面**包含本次查询需要的所有字段**，查到索引就拿到全部数据，不需要回表，`Extra`会显示`Using index`。

示例：

```sql
-- 建立覆盖索引：where查询email，只select id,name
CREATE INDEX idx_email ON users(email, id, name);
EXPLAIN SELECT id,name FROM users WHERE email='alice@example.com';
```

这条 SQL 不需要回表，Extra 出现`Using index`。

## 四、Go 数据库连接池监控代码讲解

```
import "database/sql"

func DBMetrics(db *sql.DB) {
    stats := db.Stats()
    fmt.Printf("Open: %d, InUse: %d, Idle: %d, Wait: %d\n",
        stats.OpenConnections,  // 当前总连接数
        stats.InUse,            // 正在被代码使用的连接（忙）
        stats.Idle,             // 空闲连接，等待复用
        stats.WaitCount,        // 等待连接的总次数，这个值不断上涨代表连接池不够，请求排队
    )
}
```

> 背景：`database/sql` 自带**数据库连接池**，GORM、sqlx 底层都封装了标准库的`*sql.DB`，它们本质共用这套连接池。 数据库连接是很昂贵资源，不会每次查询新建 / 销毁连接，而是提前创建一批连接放到池子里复用。

### 指标逐个解释

1. **OpenConnections**：当前连接池已经创建好的数据库连接总数（忙 + 空闲之和）

2. InUse

   ：正在被业务代码占用的连接。 比如你发起一条 SQL 查询，拿到连接执行，此时这个连接就计入**InUse**；执行完归还到池子，就变成 Idle。

   > InUse 长期很高：连接被霸占不放。**常见原因：慢 SQL、长事务**。SQL 跑几十秒不结束，连接一直被占用，别人拿不到。

3. **Idle**：空闲连接，放在池子里待命，下一次请求可以直接拿来用，不用新建连接。

4. WaitCount：有请求想拿连接，但是池子里所有连接都被用光，只能排队等待的总次数

   - 这个数字持续上涨 → 连接池不够用，请求排队。
   - 解决方案：调大 `MaxOpenConns`（连接池最大连接数量）

#### 重点：GORM 怎么拿到底层的`*sql.DB`传给这个函数

GORM 的`*gorm.DB`不是`*sql.DB`，需要获取底层原生 DB：

```go
// gormDB 是你全局的 *gorm.DB
sqlDB, err := gormDB.DB() 
if err != nil {
    panic(err)
}
DBMetrics(sqlDB) // 传入原生*sql.DB，获取连接池指标
```

> 实战场景：在 Gin 中间件、定时任务里定期调用`DBMetrics`打印指标，监控数据库连接池健康状态，提前发现线上问题。
