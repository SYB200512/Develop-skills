# 服务治理

服务治理（Service Governance）是微服务架构中**保证系统稳定、可控、可观测**的一整套机制。如果说负载均衡解决的是"流量怎么分"，那服务治理解决的是"**出问题时怎么不让系统雪崩**"

## 一、为什么需要服务治理

微服务的本质是**大量服务互相调用**，这带来了新问题：

text

```
api-gateway → user-service → db
     ↓              ↓
order-service → product-service → cache
```



一个请求可能经过 5~10 个服务。任何一个环节出问题，都会**向上传导**：

- user-service 慢 → api-gateway 线程被占满 → 整个网关不可用 → **全站雪崩**。
- 某个下游挂了 → 上游不断重试 → 把下游彻底打死 → **级联故障**。
- 突发流量 → 某个服务被打爆 → 拖垮整个链路。

**服务治理就是给这条链路加上"保险丝"和"安全阀"。**

## 二、五大核心模式

| 模式 | 目的         | 一句话比喻       | Go 常用库                                                |
| :--- | :----------- | :--------------- | :------------------------------------------------------- |
| 熔断 | 防止级联故障 | 保险丝，过载就断 | gobreaker                                                |
| 降级 | 提供兜底响应 | 备用方案         | 手动实现                                                 |
| 限流 | 保护自身资源 | 水龙头限流       | [golang.org/x/time/rate](https://golang.org/x/time/rate) |
| 重试 | 容忍临时故障 | 再试一次         | 手动 / backoff                                           |
| 超时 | 避免等待堆积 | 到点就走         | context.WithTimeout                                      |

这五个不是孤立的，而是**配合使用**的一套组合拳。

## 三、熔断

### 原理：三态状态机

熔断器本质上是一个状态机，有三个状态：

text

```
        失败率达到阈值
Closed ────────────────► Open
  ▲                       │
  │  成功                  │ 超时后
  │                       ▼
  └────────────────── Half-Open
        成功数达标
```



| 状态                  | 行为                                             |
| :-------------------- | :----------------------------------------------- |
| **Closed（关闭）**    | 正常放行所有请求，统计失败率                     |
| **Open（打开）**      | 直接拒绝所有请求，快速失败，不再打下游           |
| **Half-Open（半开）** | 放行少量请求试探，成功则回 Closed，失败则回 Open |

### 为什么能防雪崩

当下游已经挂了，继续发请求只会：

1. 浪费上游资源（连接、goroutine）。
2. 给下游更大压力，让它更难恢复。

熔断器在检测到下游异常后**直接快速失败**，不再打下游，给下游恢复的时间，同时保护上游资源。

### gobreaker 详解

```go
import "github.com/sony/gobreaker/v2"

cb := gobreaker.NewCircuitBreaker[[]byte](gobreaker.Settings{
    Name:        "user-service",
    MaxRequests: 3,                    // 半开状态最多放行 3 个请求
    Interval:    60 * time.Second,     // Closed 状态统计窗口
    Timeout:     30 * time.Second,     // Open 后等 30 秒转 Half-Open
    ReadyToTrip: func(counts gobreaker.Counts) bool {
        failureRatio := float64(counts.TotalFailures) / float64(counts.Requests)
        return counts.Requests >= 3 && failureRatio >= 0.6
    },
    OnStateChange: func(name string, from, to gobreaker.State) {
        log.Printf("circuit breaker %s: %s -> %s", name, from, to)
    },
})

body, err := cb.Execute(func() ([]byte, error) {
    resp, err := http.Get("http://user-service/api/users")
    if err != nil {
        return nil, err
    }
    defer resp.Body.Close()
    return io.ReadAll(resp.Body)
})
```

### 关键参数理解

| 参数           | 作用                    | 建议值                    |
| :------------- | :---------------------- | :------------------------ |
| `MaxRequests`  | 半开时放行多少请求试探  | 3~5                       |
| `Interval`     | Closed 状态多久清空统计 | 30~60s                    |
| `Timeout`      | Open 后多久转 Half-Open | 10~60s                    |
| `ReadyToTrip`  | 什么条件触发熔断        | 失败率 > 50% 且请求数 > N |
| `BucketPeriod` | 滚动窗口粒度（v2 新增） | 用于更平滑的统计          |
| `IsSuccessful` | 自定义什么算成功        | 比如 4xx 不算失败         |
| `IsExcluded`   | 什么错误不计入统计      | 比如 context.Canceled     |

### 状态流转细节

- **Closed → Open**：每次请求失败后调用 `ReadyToTrip`，返回 true 就转 Open。
- **Open → Half-Open**：经过 `Timeout` 后自动转。
- **Half-Open → Closed**：放行的 `MaxRequests` 个请求全部成功。
- **Half-Open → Open**：任一请求失败，立刻回 Open。

### 常见坑

- **阈值设太敏感**：偶发失败就熔断，误伤。建议"请求数 ≥ N 且失败率 ≥ X%"。
- **不区分错误类型**：把 `context.Canceled`、404 也算失败，导致误熔断。用 `IsSuccessful` / `IsExcluded` 过滤。
- **熔断后没有降级**：直接返回错误给用户，体验差。要和降级配合。
- **每个下游一个熔断器**：不要全局共用一个，否则一个下游挂影响所有调用。

## 四、降级（Fallback）

### 是什么

当熔断、超时、限流触发时，**返回一个兜底响应**，而不是直接报错。

### 三种降级策略

| 策略                | 例子                         |
| :------------------ | :--------------------------- |
| **返回缓存/默认值** | 商品详情挂了，返回缓存的价格 |
| **返回简化数据**    | 推荐服务挂了，返回热门榜单   |
| **静默失败**        | 日志上报失败，不告诉用户     |

### Go 实现（手动）

```go
func GetUser(ctx context.Context, id int) (*User, error) {
    // 走熔断器
    result, err := cb.Execute(func() (interface{}, error) {
        return userClient.GetUser(ctx, id)
    })
    if err != nil {
        // 降级：返回缓存或默认值
        if cached, ok := cache.Get(fmt.Sprintf("user:%d", id)); ok {
            log.Printf("fallback to cache for user %d", id)
            return cached.(*User), nil
        }
        return &User{ID: id, Name: "未知用户"}, nil
    }
    return result.(*User), nil
}
```

### 降级的原则

- **降级要有业务意义**：返回默认值不能导致业务错误（比如返回 0 元订单）。
- **降级要可观测**：记录日志/指标，知道什么时候触发了降级。
- **降级要能恢复**：下游恢复后自动切回正常逻辑。
- **不是所有接口都能降级**：支付、扣库存这类强一致操作不能降级。

## 五、限流（Rate Limiting）

### 为什么需要

保护自身不被突发流量打垮。**限流是保护自己，熔断是保护下游**，两者方向相反。

### 常见算法

| 算法     | 原理           | 特点                 |
| :------- | :------------- | :------------------- |
| 计数器   | 固定窗口计数   | 简单，有临界问题     |
| 滑动窗口 | 细分窗口       | 平滑，实现稍复杂     |
| 漏桶     | 恒定速率流出   | 平滑流量，不允许突发 |
| 令牌桶   | 恒定速率放令牌 | 允许一定突发，最常用 |

### Go 标准库 `golang.org/x/time/rate`

基于**令牌桶**算法：

```go
import "golang.org/x/time/rate"

// 每秒 100 个请求，桶容量 200（允许突发 200）
limiter := rate.NewLimiter(100, 200)

func handler(w http.ResponseWriter, r *http.Request) {
    if !limiter.Allow() {
        http.Error(w, "too many requests", http.StatusTooManyRequests)
        return
    }
    // 正常处理
}
```

### 三种限流方式

```go
// 1. Allow：不等待，直接判断
if limiter.Allow() { ... }

// 2. Wait：阻塞等待直到有令牌
if err := limiter.Wait(ctx); err != nil { ... }

// 3. Reserve：预约，返回需要等待的时间
r := limiter.Reserve()
if !r.OK() { ... }
time.Sleep(r.Delay())
```

### 限流维度

| 维度       | 场景             |
| :--------- | :--------------- |
| 全局限流   | 保护整个服务     |
| 按用户限流 | 防止单用户刷接口 |
| 按 IP 限流 | 防止单 IP 攻击   |
| 按接口限流 | 保护核心接口     |

### 分布式限流

单机 `rate.Limiter` 只在单实例生效。多实例要全局限流，需要：

- **Redis + Lua 脚本**：原子计数。
- **Sentinel / Hystrix**：专门的限流组件。
- **网关层限流**：Nginx `limit_req`、API 网关。

nginx

```nginx
# Nginx 限流
limit_req_zone $binary_remote_addr zone=perip:10m rate=10r/s;

location /api/ {
    limit_req zone=perip burst=20 nodelay;
    proxy_pass http://backend;
}
```

### 常见坑

- **限流阈值拍脑袋**：要压测得出，不是猜的。
- **被限流返回 500**：应该返回 `429 Too Many Requests`。
- **单机限流当全局用**：10 个实例各限 100，实际全局是 1000。
- **限流后没提示**：客户端不知道被限流，应该返回 `Retry-After`。

## 六、重试（Retry）

### 为什么需要

网络抖动、下游临时 GC、偶发超时，重试一次往往就好了。

### 重试的三个铁律

**1. 只重试幂等操作**

- ✅ GET、PUT、DELETE（幂等）
- ❌ POST 创建订单、扣款（非幂等，重试会重复下单）

**2. 必须退避（Backoff）**

不要立即重试，否则会把下游打死：

```go
import "github.com/cenkalti/backoff/v4"

operation := func() error {
    return callDownstream()
}

// 指数退避：100ms, 200ms, 400ms, 800ms... 最多 30s
err := backoff.Retry(operation, backoff.NewExponentialBackOff())
```

**3. 必须限制次数和时间**

```go
bo := backoff.NewExponentialBackOff()
bo.MaxElapsedTime = 5 * time.Second   // 总超时
bo.MaxInterval = 1 * time.Second      // 单次最大间隔

err := backoff.Retry(operation, backoff.WithMaxRetries(bo, 3))
```

### 重试放大问题（Retry Storm）

```text
gateway 重试 3 次 → 每个请求变 3 个
    ↓
service A 重试 3 次 → 9 个
    ↓
service B 重试 3 次 → 27 个
```

**重试次数会指数放大**，可能把下游彻底打死。所以：

- 只在**最靠近用户的一层**重试，内部服务不重试。
- 或者用**重试预算**（Retry Budget）：只允许 10% 的请求重试。

### 重试 + 熔断配合

重试失败会推高失败率，触发熔断。这是好事：**熔断后就不重试了**，避免重试风暴。

```go
package main

import (
	"fmt"
	"log"
	"net/http"
	"time"

	"github.com/cenkalti/backoff/v4"
)

// 调用下游，幂等GET接口
func callUserService() error {
	resp, err := http.Get("http://user-service/api/users")
	if err != nil {
		log.Printf("http get failed: %v", err)
		return err // 返回error → backoff会重试
	}
	defer resp.Body.Close()

	// 下游5xx服务端错误，我们也认为临时故障，需要重试
	if resp.StatusCode >= 500 {
		return fmt.Errorf("downstream 5xx error: %s", resp.Status)
	}

	log.Println("call user service success")
	return nil // 返回nil → 成功，停止重试
}

func main() {
	// 1. 创建指数退避器
	bo := backoff.NewExponentialBackOff()
	bo.MaxElapsedTime = 5 * time.Second // 整个重试流程最多总耗时5s
	bo.MaxInterval = 1 * time.Second    // 两次重试之间最大间隔（不会超过1s）

	// 2. 限制最多重试3次（原始指数退避是无限重试！必须限制）
	limitedBO := backoff.WithMaxRetries(bo, 3)

	// 3. 执行重试逻辑
	err := backoff.Retry(callUserService, limitedBO)
	if err != nil {
		log.Printf("all retry failed, final err: %v", err)
		return
	}
	log.Println("finish")
}
```

## 七、超时（Timeout）

### 为什么需要

没有超时，一个慢请求会**永久占用 goroutine 和连接**，最终耗尽资源。

### Go 实现：context

```go
ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
defer cancel()

resp, err := client.GetUser(ctx, req)
if err != nil {
    if errors.Is(err, context.DeadlineExceeded) {
        log.Println("timeout")
    }
}
```

### 超时的层级传递

**关键原则：上游超时必须大于下游超时之和。**

```text
gateway 超时 3s
  └─ user-service 超时 2s
       └─ db 超时 1s
```

如果反过来（gateway 1s，db 2s），db 还没超时，gateway 已经放弃了，白干活。

### 超时预算

一个请求经过多个服务，总超时要合理分配：

```text
总预算 3s
├─ gateway 自身处理：0.1s
├─ user-service：1s
├─ order-service：1s
└─ 预留：0.9s
```

gRPC 支持**超时传播**：客户端设的 deadline 会自动传给服务端，服务端不用重新设。

### 常见坑

- **不设超时**：默认永不超时，连接泄漏。
- **超时设太长**：等于没设，资源还是被占。
- **超时设太短**：正常请求被误杀。
- **各层超时不一致**：上游比下游短，下游白干。
- **超时后没 cancel**：goroutine 泄漏。务必 `defer cancel()`。

## 八、五大模式如何组合

这五个模式不是独立的，而是**一条完整的请求处理链**：

```go
package service

import (
	"context"
	"fmt"
	"log"
	"time"

	"github.com/cenkalti/backoff/v4"
)

// CallUserService 调用用户服务，带超时、限流、熔断、重试、降级
func CallUserService(ctx context.Context, id int) (*User, error) {
	// 1. 限流：最先做，最廉价，保护自己
	if !limiter.Allow() {
		metrics.Inc("user_service_ratelimited_total")
		// 限流也走降级，语义统一
		return getDefaultUser(id), nil
	}

	// 2. 总超时：整个调用最多 3 秒
	ctx, cancel := context.WithTimeout(ctx, 3*time.Second)
	defer cancel()

	// 3. 配置退避策略（显式参数，避免默认值过大）
	b := backoff.NewExponentialBackOff()
	b.InitialInterval = 100 * time.Millisecond
	b.MaxInterval = 500 * time.Millisecond
	b.MaxElapsedTime = 0 // 不按时间停，由 MaxRetries + ctx 控制

	var result *User

	// 4. 重试：最多 3 次尝试（1 次 + 2 次重试），且受 ctx 约束
	operation := func() error {
		// 4.1 每次尝试独立超时，避免一次慢调用吃掉全部预算
		attemptCtx, attemptCancel := context.WithTimeout(ctx, 1*time.Second)
		defer attemptCancel()

		// 4.2 熔断器包裹实际调用
		resp, err := cb.Execute(func() (interface{}, error) {
			return userClient.GetUser(attemptCtx, id)
		})
		if err != nil {
			// 熔断器 open 属于"快速失败"，重试没意义，直接返回
			if err == ErrCircuitOpen {
				return backoff.Permanent(err)
			}
			return err
		}

		// 4.3 安全类型断言，避免 panic
		u, ok := resp.(*User)
		if !ok {
			return backoff.Permanent(fmt.Errorf("unexpected type %T", resp))
		}
		result = u
		return nil
	}

	// 4.4 backoff.WithContext 让 sleep 阶段也能感知 ctx 取消
	err := backoff.Retry(
		operation,
		backoff.WithContext(backoff.WithMaxRetries(b, 2), ctx),
	)

	// 5. 降级：最终失败返回兜底
	if err != nil {
		log.Printf("CallUserService fallback, id=%d, err=%v", id, err)
		metrics.Inc("user_service_fallback_total")
		return getDefaultUser(id), nil
	}

	return result, nil
}
```

**执行顺序**：

```text
1. 进入函数 → limiter 限流判断，限流直接返回兜底。
2. 创建外层 ctx：总超时 3 秒，defer cancel。
3. 初始化指数退避策略。
4. backoff.Retry 启动重试循环（最多尝试 3 次）
   - 每次重试：新建 1s 单次调用 ctx
   - cb.Execute 执行远程调用，熔断器记录本次结果
   - 如果熔断器 Open → 返回 Permanent 错误，直接终止重试
   - 如果普通错误 → backoff 等待退避时间，继续重试
   - 如果成功 → operation 返回 nil，终止重试
5. 重试全部失败 → 进入降级，返回兜底用户。
6. 重试成功 → 返回真实用户数据。
```

## 九、面试常见问题

**Q1：熔断和限流的区别？**

> 熔断是**保护下游**：下游挂了就断开，不再打它，防止级联故障。限流是**保护自己**：限制进入的流量，防止自己被压垮。方向相反。

**Q2：熔断器的三个状态？**

> Closed（正常放行+统计）、Open（直接拒绝）、Half-Open（放少量试探）。失败率超阈值 Closed→Open，超时后 Open→Half-Open，试探成功回 Closed，失败回 Open。

**Q3：重试要注意什么？**

> 三点：只重试幂等操作、必须指数退避、必须限制次数和总时间。还要防重试风暴，重试次数会指数放大。

**Q4：超时怎么设？**

> 上游超时 > 下游超时之和。用 context 传递 deadline，gRPC 会自动传播。每个超时都要 `defer cancel()` 防泄漏。

**Q5：降级怎么做？**

> 返回缓存、默认值或简化数据。要保证降级结果有业务意义，不能导致业务错误。强一致操作（支付）不能降级。降级要可观测、可恢复。

**Q6：这五个模式怎么组合？**

> 限流 → 超时 → 熔断 → 重试 → 降级。限流保护自己，超时防堆积，熔断防雪崩，重试容忍抖动，降级兜底体验。

## 十、落地建议

### 优先级

```text
第 1：超时          ← 最简单，收益最大，必做
第 2：限流          ← 保护自己，防突发
第 3：熔断          ← 防雪崩，微服务必备
第 4：降级          ← 提升体验，配合熔断
第 5：重试          ← 谨慎使用，容易放大问题
```

### 每个服务都要有

- 所有外部调用设超时。
- 所有入口设限流。
- 所有下游调用包熔断器。
- 关键接口有降级方案。
- 重试只用在幂等且最外层。

### 可观测性

服务治理必须配合监控：

- 熔断器状态变化打点。
- 限流触发次数。
- 重试次数和成功率。
- 超时率、P99 延迟。
- 降级触发次数。

没有监控的服务治理等于没有。
