# Go GC 三色标记‑清除 + GOGC / GOMEMLIMIT + GC 性能问题

## 一、三色标记‑清除（Concurrent Tri‑Color Mark‑Sweep）

> Go1.5 正式引入，**并发 GC**：大部分 GC 工作和业务 goroutine 并行，只有两处短暂 STW，降低业务停顿。 STW (Stop The World)：暂停全部用户 goroutine，业务代码不再执行。

### 1. 三色定义

堆上所有对象划分为 3 种颜色：

1. **白色**：尚未扫描；标记结束后仍然白色 → 垃圾，等待回收。
2. **灰色**：对象已经被发现可达，但是它的子指针还没有遍历扫描完成，放入标记队列。
3. **黑色**：对象本身 + 它全部子对象全部扫描完毕，确定存活，不会被回收。

> 根对象：栈上变量、全局变量，从根出发能访问到的对象 = 存活对象。

基础流程：

1. GC 开始，全部对象初始白色；把根可达对象置为灰色，入标记队列。
2. 取出灰色对象：把它引用的白色子对象改成灰色；自身改为黑色。
3. 循环消费灰色队列，直到没有灰色对象。
4. 标记结束：黑色 = 存活；白色 = 垃圾。

### 2. 并发标记的致命问题：漏标

GC 和业务 goroutine 同时跑，业务会修改指针，会出现这个情况：

> **黑色对象，新增引用指向白色对象；而该白色对象不再被灰色 / 其他对象引用。**

此时：黑色不会再被扫描；白色没人处理，会被错误当成垃圾回收，程序崩溃。

✅解决方案：**写屏障 Write Barrier** 只要发生`黑色对象 → 白色对象`的引用赋值，写屏障强制把这个白色对象置为灰色，送入标记队列，保证不会漏扫描。

> Go 使用的是**混合写屏障**，Go1.8 之后启用，消除了对栈的二次扫描，进一步缩短 STW 时间。

### 3. GC 完整 4 个阶段

表格

| 阶段                      | 工作内容                                                    | 是否 STW              |
| ------------------------- | ----------------------------------------------------------- | --------------------- |
| Mark Setup 标记准备       | 开启混合写屏障，初始化 GC 数据结构                          | ✅ STW（极短，微秒级） |
| Marking 并发标记          | GC worker 协程 + 业务协程并行标记堆对象；写屏障捕获指针修改 | ❌ 并发，不停业务      |
| Mark Termination 标记终止 | 处理剩余灰色对象，确保全部标记完成；关闭写屏障              | ✅ STW（短）           |
| Sweep 清扫回收            | 回收白色垃圾对象；**懒清扫（延迟清扫）**                    | ❌ 并发                |

> **懒清扫 Sweep：不会一次性遍历整个堆释放内存。** 垃圾不会立刻释放；**当程序申请新内存的时候，顺便清扫回收空闲块**还给堆。 现象：GC 完成后 RSS 内存不会立刻下降，后续分配内存才逐步降。

### 关键记忆点

1. Go GC **不是分代 GC**，没有新生代老年代，全部对象统一三色标记。
2. 只有 Setup、Termination 两处 STW；主要耗时的标记、清扫全部并发。
3. 混合写屏障解决并发标记漏标问题。
4. 清扫是懒清扫。

## 二、GOGC 和 GOMEMLIMIT 调优

### 1. GOGC（老的传统阈值，按堆增长比例）

环境变量，默认值 `GOGC=100`。

> 触发逻辑：**上一次 GC 完成后，存活堆内存大小 × (1 + GOGC/100)**，达到该堆大小，触发新一轮 GC。

举例： 上一轮 GC 结束，存活对象占用 100MB

- GOGC=100：堆涨到 `100 * (1+100/100) = 200MB` 触发 GC。

调优方向：

1. **GOGC 调大（例如 200）** 允许堆涨更多才 GC；GC 次数变少，CPU 开销下降；**内存占用变高**。适合内存充裕场景。
2. **GOGC 调小（例如 30）** 更早触发 GC；GC 更加频繁；CPU 开销上升；**内存占用降低**。适合内存紧张。
3. `GOGC=off`：关闭 GC，只在程序退出做一次回收；**生产禁止，只做测试**。

> 缺点：GOGC 是相对比例。如果存活堆本身很大，允许增长的绝对内存也会很大，容易 OOM。于是 Go1.19 引入 GOMEMLIMIT。

### 2. GOMEMLIMIT（Go1.19+，内存硬上限，推荐优先使用）

设置 GC 的目标软内存上限（单位字节）。

> 告诉 Go：**尽量不要让 Go 堆内存超过这个值；接近该值就主动触发 GC，即使 GOGC 条件还没到。**

示例：

```
# 设置堆目标上限 512MB
GOMEMLIMIT=536870912 ./app
```

#### GOMEMLIMIT 工作逻辑

1. 当 Go 堆内存接近 GOMEMLIMIT，会**无视 GOGC 阈值，强制提早 GC**，把堆压下来，防止 OOM。
2. 不是绝对硬限制，瞬时可能超过；是 GC 调度的目标。
3. 设置为 `GOMEMLIMIT=0`，代表关闭该特性，完全只用 GOGC 逻辑。

> 最佳实践：容器部署环境，**优先配置 GOMEMLIMIT，不要只依赖 GOGC**。 容器 limit 是 1GiB，可以给 GOMEMLIMIT 设置为 700‑800MiB，预留一部分给内核、cgo、栈等非 Go 堆内存。

### 两者配合关系

1. 没有设置 GOMEMLIMIT：完全按照 GOGC 比例触发 GC。
2. 设置 GOMEMLIMIT：哪个条件先满足，就触发 GC。
   - 要么堆增长达到 GOGC 比例；
   - 要么堆接近 GOMEMLIMIT 上限。

> 额外强制触发条件：无论 GOGC/GOMEMLIMIT，**2 分钟没有 GC，强制跑一次 GC**；也可以手动`runtime.GC()`。

### 调优经验

1. 内存充足，追求低 CPU：调大 GOGC，设置合理 GOMEMLIMIT 作为安全兜底。
2. 容器内存紧张：**一定要开 GOMEMLIMIT**，防止 GOGC 模式下堆暴涨 OOM。
3. 不要盲目把 GOGC 调很小，GC 太频繁会大量占用 CPU，业务吞吐量下降。

## 三、GC 引发性能问题场景 & 解决方案

> GC 带来的性能问题两类：
>
> 1. STW 停顿太长，请求延迟抖动；
> 2. GC 太频繁，GC CPU 占用高，业务吞吐量下降。

### 场景 1：大量短期小对象，GC 频繁，CPU 高

现象： pprof 看到`gc mark phase`CPU 占比很高；GC 次数非常多；每次 GC 堆不大，但是不停 GC。 原因：业务循环、请求里面疯狂创建大量短生命周期小对象，堆快速膨胀，反复触发 GC。

解决方案：

1. 对象复用：sync.Pool，复用临时对象，减少堆分配，减少垃圾生成。
2. 尽量使用值类型，减少逃逸；避免变量逃逸到堆（`go build -gcflags=-m`查看逃逸分析）。
3. 拼接字符串用 strings.Builder，不要大量`+`拼接产生临时字符串。
4. 适当调大 GOGC，降低 GC 频率；有容器设置 GOMEMLIMIT 兜底。

### 场景 2：STW 停顿时间长，接口偶发延迟毛刺

三色标记只有两处 STW，正常是微秒级；STW 变长常见诱因：

1. **大量 goroutine，栈扫描耗时**。Mark Setup 阶段 STW 需要扫描各个 goroutine 栈；goroutine 数量几万十几万，STW 会上涨。
2. 瞬时产生巨量对象，标记阶段压力大，Mark Termination 收尾阶段 STW 被拉长。

解决方案：

1. 控制 goroutine 数量，不要无限制 go func ()，使用 worker 池做限流。
2. 减少瞬时大量对象分配，打散流量。
3. Go 新版本升级，混合写屏障、GC 持续优化。

### 场景 3：内存持续上涨，GC 后内存不下降，怀疑内存泄漏

> 注意区分两种现象：

1. **不是泄漏：懒清扫 Sweep** GC 标记完成只是标记垃圾；内存不会立刻还给 OS。内存 RSS 高，但是堆内空闲块很多，Go 留给后续分配复用。 可以看 go runtime 指标：`heap_inuse`（正在使用） vs `heap_sys`（向操作系统申请的总内存）。heap_inuse 已经降了，RSS 不降，属于正常。
2. **真内存泄漏：对象被长期存活的指针持有（slice、map、全局变量、channel 没有释放），对象变成存活，GC 无法回收。** 比如 slice 保留不再需要的底层数组、map 持续插入不清理、goroutine 泄露永久持有对象。

排查：pprof heap，对比 inuse_objects，定位持续增长对象。 解决：切断长生命周期对短生命周期对象的引用；及时释放 map/slice；杜绝 goroutine 泄漏。

### 场景 4：容器环境 OOM，GOGC 模式下堆无节制上涨

现象：容器内存打满被 kill；GOGC=100，存活堆本身就很大，允许翻倍增长，直接超过容器 limit。

解决方案：**启用 GOMEMLIMIT，设置低于容器 limit，给 GC 一个内存上限，提前触发 GC，避免 OOM。**

### 场景 5：大对象频繁分配

大对象直接进入大对象堆；大量大对象会加重 GC 标记压力。 方案：尽量复用大对象；避免循环内重复创建大 slice。

### 排查 GC 问题工具

1. `GODEBUG=gctrace=1 ./app`，控制台打印每次 GC 信息：GC 耗时、STW 时间、堆大小。
2. pprof：`net/http/pprof`，看 heap、goroutine profile。
3. prometheus 采集 go runtime 指标：`go_gc_duration_seconds`、`go_memstats_heap_inuse_bytes`。

# 面试速记总结

1. Go GC 是**并发三色标记清除，混合写屏障解决漏标；两阶段 STW；清扫是懒清扫**。
2. GOGC：按存活堆的百分比触发 GC；调大减少 GC 次数，内存上升；调小 GC 变频繁 CPU 升高。
3. GOMEMLIMIT (go1.19+)：堆内存软上限，容器环境优先使用，防止 OOM，作为兜底。
4. GC 性能问题：
   - 大量小对象 → GC 频繁 CPU 高 → sync.Pool、减少堆逃逸。
   - STW 毛刺 → 控制 goroutine 数量。
   - RSS 高不一定泄漏，区分懒清扫；真泄漏排查长生命周期引用。
   - 容器 OOM，务必开启 GOMEMLIMIT。
