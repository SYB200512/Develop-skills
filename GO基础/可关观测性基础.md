# 可关观测性基础

## 一、可观测性

可观测性（Observability）是**通过外部输出的信号，判断系统内部运行状态**的能力。它解决的核心问题：**系统出了问题，你能不能问出 "为什么"**，而不是只能问 "有没有出问题"。

- **监控（Monitoring）**：告诉我们系统 "是否坏了"（红灯 / 绿灯）。
- **可观测性（Observability）**：更进一步，告诉我们 "为什么坏了、坏在哪里"。

现代分布式系统由几十上百个服务组成，一个请求会跨多个服务、数据库、缓存、消息队列。这时候光靠 "这个服务挂了" 远远不够，你需要把整个链路看清楚 —— 这就是可观测性存在的意义。

## 二、三大支柱

| 支柱                | 本质                      | 数据特征                                   | 典型工具              |
| ------------------- | ------------------------- | ------------------------------------------ | --------------------- |
| **日志 Logs**       | 记录 "发生了什么"         | 离散事件，一段文本，带时间戳               | ELK、Loki、Devslog    |
| **指标 Metrics**    | 记录 "状态怎么样"         | 聚合的数值，随时间采样（计数、速率、分布） | Prometheus、Grafana   |
| **链路追踪 Traces** | 记录 "一个请求走了哪条路" | 请求生命周期，树状跨多个服务               | Jaeger、OpenTelemetry |

- **Logs** 问 "到底发生了什么"（报错、慢查询、用户操作）。
- **Metrics** 问 "整体趋势怎么样"（QPS 下降、延迟升高、CPU 打满）。
- **Traces** 问 "这个请求具体经历了什么"（哪一环慢、哪一环失败）。

## 三、三者如何配合（这是重点）

三者不是孤立的，而是**一条 Trace 把 Logs 和 Metrics 串起来**：

- 一个**用户请求** → 生成一条 **Trace（带唯一 Trace ID）**
- Trace 由多个 **Span（跨度 / 片段）** 组成，每个 Span 代表一个操作（如 `HTTP GET /api/users`、`DB query`、`Cache lookup`）
- **每个 Span 上挂载**对应的 **Log**（细节证据）和 **Metric**（量化数据）

数据流是这样的：

```plaintext
用户请求
  └─ Trace: request-123
      ├─ Span: HTTP GET /api/users
      │   ├─ Log:   "query executed in 15ms"
      │   └─ Metric: http_request_duration_ms{method="GET"} 15
      ├─ Span: DB query
      │   ├─ Log:   "rows returned: 42"
      │   └─ Metric: db_query_count{query="users"} +1
      └─ Span: Cache lookup
```

**所以真相是：Logs 是 "证据"，Metrics 是 "体检报告"，Traces 是 "病例档案"。** 三者用同一个 Trace ID 关联起来，排查问题时你才能从指标里发现异常 → 顺着 Trace 定位到某个 Span → 再翻这条 Span 的 Log 找到根因。

## 四、Go 中的落地：OpenTelemetry

课程给的 Go 代码就是最佳实践，关键两点：

```go
import (
    "go.opentelemetry.io/otel"
    "go.opentelemetry.io/otel/trace"
)

tracer := otel.Tracer("user-service")

func GetUser(ctx context.Context, id string) (*User, error) {
    ctx, span := tracer.Start(ctx, "GetUser")  // ① 开启 Span
    defer span.End()                             // ② 结束 Span

    span.SetAttributes(attribute.String("user.id", id))  // ③ 打属性标签
    // ...业务逻辑
}
```

**四个要点，对应你的代码：**

1. **必须透传 `ctx`**：`tracer.Start(ctx, ...)` 依赖 ctx 携带 Trace ID。这就是为什么 Go 里函数第一个参数永远是 `ctx context.Context`—— 它把链路信息一路传下去。

2. **`defer span.End()`**：确保 Span 无论成功失败都被结束，否则链路数据不完整。

3. **`SetAttributes`** 打标签：`user.id`、`order.id` 这类维度信息，方便以后按这些标签检索、筛选 Trace。

4. **统一标准**：OpenTelemetry 是一套跨语言的标准 SDK，配上 Jaeger 做可视化后端，一套代码同时产出 Trace，且能关联 Logs/Metrics。

## 五、工具怎么选（什么时候用什么）

| 场景                         | 用什么                              | 为什么                                   |
| ---------------------------- | ----------------------------------- | ---------------------------------------- |
| 看服务健康度、告警           | **Metrics**（Prometheus + Grafana） | 数值稳定、易存储、适合长期趋势和阈值告警 |
| 排查一次具体报错 / 崩溃      | **Logs**（ELK / Loki）              | 有完整细节上下文                         |
| 跨服务定位慢请求、追踪调用链 | **Traces**（Jaeger / OTel）         | 能看到请求全路径和每段耗时               |
| 三个一起搭                   | **OpenTelemetry + Grafana 全家桶**  | 统一标准，三支柱同源关联                 |

**核心记忆点：**

1. 可观测性 ≠ 日志，是**三大支柱协同**，缺一不可。
2. **Traces 是骨架，Logs 是细节，Metrics 是趋势**，靠 Trace ID 把三者串成一条线。
3. Go 里就是**死守 `ctx` 透传 + `defer span.End()`**，靠 OpenTelemetry 一套代码产出全部信号。
