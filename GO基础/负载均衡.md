# 负载均衡

## 一、原因

单台服务器存在三个天花板：

1. **性能天花板**：CPU、内存、网络带宽有限，QPS 到顶就扛不住。
2. **可用性天花板**：一台机器宕机，整个服务就挂了。
3. **扩展性天花板**：无法通过加机器线性提升容量。

负载均衡解决的就是：

- **水平扩展**：加机器就能提升整体处理能力。
- **故障隔离**：某台挂了，流量自动切到健康节点。
- **资源优化**：把请求分给负载低的节点，避免有的忙死、有的闲死。
- **灰度/发布**：可按权重把少量流量导入新版本。



## 二、负载均衡的层次

| 层次      | 典型实现                          | 工作依据            | 常见算法                       |
| :-------- | :-------------------------------- | :------------------ | :----------------------------- |
| DNS 层    | DNS 轮询、GeoDNS                  | 域名解析            | 轮询、地理位置                 |
| 传输层 L4 | LVS、**Nginx stream**、HAProxy    | IP + 端口           | least_conn、hash、rr           |
| 应用层 L7 | **Nginx http**、Envoy、Traefik    | HTTP 头/路径/Cookie | 加权轮询、IP hash、一致性 hash |
| 客户端层  | gRPC pick_first、Ribbon、Go micro | 服务发现 + 本地策略 | 轮询、权重、                   |

### 1. DNS 层负载均衡

最简单的方式：一个域名解析到多个 IP，DNS 服务器轮流返回。

**优点**：实现简单，无需额外设备。
**缺点**：

- DNS 缓存导致切换不及时（TTL 内故障无法摘除）。
- 无法感知后端真实负载。
- 客户端可能一直用同一个 IP。

### 2. L4 传输层负载均衡

只看 IP 和端口，不解析应用层协议，性能极高（LVS 可做到百万级并发）。

- **NAT 模式**：改目标 IP，回包也经过 LB。
- **DR 模式**：只改 MAC，回包直接由后端返回，LB 只处理入向流量。
- **TUN 模式**：IP 隧道封装。

### 3. L7 应用层负载均衡

能看懂 HTTP，可以做：

- 按 URL 路径路由（`/api` → 服务 A，`/static` → 服务 B）。
- 按 Header/Cookie 做会话保持。
- 内容改写、限流、鉴权。
- 更精细的健康检查。

代价是性能低于 L4，且 LB 本身更容易成为瓶颈。

### 4. 客户端负载均衡

把负载均衡逻辑放到调用方（gRPC、Ribbon 等）：

- 客户端从服务注册中心（Consul/Etcd/Nacos）拿到实例列表。
- 本地按策略选一个实例直连。
- 少一跳网络，延迟更低；但每个语言都要实现一套逻辑。

## 三、常见负载均衡算法

### 1. 轮询（Round Robin）

请求依次分给每个后端。适合后端性能一致的场景。

### 2. 加权轮询（Weighted RR）

给性能强的机器更高权重。

```nginx
upstream user_service {
    server 10.0.0.1:8080 weight=3;
    server 10.0.0.2:8080 weight=2;
    server 10.0.0.3:8080 weight=1;
}
```

比例 3:2:1，6 个请求里分别分到 3、2、1 个。

### 3. 最少连接（Least Connections）

把请求发给当前连接数最少的节点，适合长连接、请求耗时差异大的场景。

```nginx
upstream user_service {
    least_conn;
    server 10.0.0.1:8080;
    server 10.0.0.2:8080;
}
```

### 4. IP Hash / 一致性 Hash

同一客户端 IP 固定落到同一后端，实现**会话保持**。

```nginx
upstream user_service {
    ip_hash;
    server 10.0.0.1:8080;
    server 10.0.0.2:8080;
}
```

一致性 Hash 在节点增加时只影响少量 key，常用于缓存场景。

### 5. 最短响应时间（Least Time）

Nginx Plus 支持，综合连接数和响应时间选择。

### 6. P2C（Power of Two Choices）

随机挑两个节点，选负载低的那个。gRPC、Envoy 常用，效果接近最优且开销小。

### 7. 随机（Random）

简单随机，节点多时接近均匀。

## 四、健康检查与熔断

负载均衡必须配合健康检查，否则会把流量打到挂掉的节点。

- **被动检查**：根据请求失败率判断，Nginx 的 `max_fails`、`fail_timeout`。
- **主动检查**：定时探活（Nginx Plus、Envoy、gRPC health check）。
- **熔断**：连续失败达到阈值就暂时剔除，过一段时间半开重试。

```nginx
upstream user_service {
    least_conn;
    server 10.0.0.1:8080 max_fails=3 fail_timeout=10s;
    server 10.0.0.2:8080 max_fails=3 fail_timeout=10s;
    server 10.0.0.3:8080 backup;   # 备用节点
}
```

- `max_fails=3`：10 秒内失败 3 次就标记不可用。
- `fail_timeout=10s`：不可用持续 10 秒后重新尝试。
- `backup`：主节点全挂时才启用。

## 五、Go gRPC 客户端负载均衡

gRPC 天然支持客户端负载均衡，核心是 **Resolver + Balancer** 两个扩展点。

### 1. 基本用法

```go
package main

import (
	"log"
	"google.golang.org/grpc"
	pb "your-module/proto/user"
)

func main() {
	conn, err := grpc.Dial(
		"dns:///user-service:8080",
		grpc.WithDefaultServiceConfig(`{
			"loadBalancingConfig": [{"round_robin": {}}]
		}`),
	)
	if err != nil {
		log.Fatal(err)
	}
	defer conn.Close()
	client := pb.NewUserServiceClient(conn)

	// RPC调用部分
	ctx := context.Background()
	resp, err := client.GetUser(ctx, &pb.GetUserRequest{Id: 1001})
	if err != nil {
		log.Println("rpc call failed:", err)
		return
	}
	log.Println("resp:", resp)
}

```

- `dns:///user-service:8080`：用 DNS resolver 解析出多个 IP。
- `round_robin`：gRPC 内置的轮询 balancer。
- 其他内置策略：`pick_first`（默认，只用一个地址）、`grpclb`（外部 LB）。



- `conn`：一条**通信管道（连接池）**，长期存在。
- `client`：**装在管道一头的遥控器**，上面有各种按钮（GetUser 等 RPC 方法），遥控器持有管道。
- `ctx`：**每按一次按钮时附带的指令**：“这个请求最多等 2 秒，可以随时取消”。

> 管道 (conn)、遥控器 (client) 只创建一次反复用；**每次按按钮（发起 RPC），都可以带一个全新的 ctx 指令**

### 2. 结合服务发现（如 Consul/Etcd）

生产环境一般用自定义 resolver：

```go
import "google.golang.org/grpc/resolver"

type consulResolver struct {
    target resolver.Target
    cc     resolver.ClientConn
}

func (r *consulResolver) ResolveNow(resolver.ResolveNowOptions) {
    addrs := queryConsul(r.target.Endpoint()) // 从 Consul 拿实例列表
    state := resolver.State{}
    for _, a := range addrs {
        state.Addresses = append(state.Addresses, resolver.Address{Addr: a})
    }
    r.cc.UpdateState(state)
}
```

注册后：

```go
resolver.Register(&consulBuilder{})
conn, _ := grpc.Dial("consul:///user-service",
    grpc.WithDefaultServiceConfig(`{"loadBalancingConfig":[{"round_robin":{}}]}`))
```

### 3. 加权负载均衡

gRPC 支持通过地址属性传权重，自定义 balancer 读取权重实现加权轮询。也可以用 `weighted_target` 策略：

```json
{
  "loadBalancingConfig": [{
    "weighted_target": {
      "targets": {
        "v1": { "weight": 80, "childPolicy": [{"round_robin": {}}] },
        "v2": { "weight": 20, "childPolicy": [{"round_robin": {}}] }
      }
    }
  }]
}
```

适合灰度发布：80% 流量走 v1，20% 走 v2。

## 六、Nginx 配置实战

### 1. L7 HTTP 负载均衡

```nginx
http {
    upstream user_service {
        least_conn;
        server 10.0.0.1:8080 weight=3 max_fails=3 fail_timeout=10s;
        server 10.0.0.2:8080 weight=2 max_fails=3 fail_timeout=10s;
        server 10.0.0.3:8080 backup;
        keepalive 32;          # 与后端保持长连接
    }

    server {
        listen 80;
        location /api/users/ {
            proxy_pass http://user_service;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_next_upstream error timeout http_502;  # 失败自动重试下一台
        }
    }
}
```

关键指令：

- `weight`：权重。
- `backup`：备用节点。
- `down`：手动下线。
- `keepalive`：连接池，减少握手开销。
- `proxy_next_upstream`：失败转移到下一台。

### 2. L4 TCP 负载均衡（stream 模块）

```nginx
stream {
    upstream mysql_cluster {
        least_conn;
        server 10.0.0.11:3306;
        server 10.0.0.12:3306;
    }

    server {
        listen 3306;
        proxy_pass mysql_cluster;
    }
}
```

适合数据库、Redis、gRPC（非 HTTP/2 终止）等场景。

### 3. 一致性 Hash（缓存场景)

```nginx
upstream cache_cluster {
    hash $request_uri consistent;
    server 10.0.0.21:6379;
    server 10.0.0.22:6379;
    server 10.0.0.23:6379;

```

`consistent` 开启一致性 Hash，节点增减时只影响部分 key。



# 实战：Nginx 配 upstream + 健康检查

### 目标

能用 Nginx 把请求分发到多个 Go 服务实例，并让挂掉的实例自动被摘除。

| 概念                | 含义                      |
| :------------------ | :------------------------ |
| upstream            | 一组后端服务器的集合      |
| server              | upstream 里的一个后端地址 |
| weight              | 权重，默认 1              |
| backup              | 备用节点，主节点全挂才用  |
| down                | 手动标记下线              |
| max_fails           | 失败几次标记不可用        |
| fail_timeout        | 标记不可用后多久重试      |
| proxy_next_upstream | 失败时自动重试下一台      |
| keepalive           | 与后端保持长连接的数量    |

### 实操步骤

**1. 起两个 Go 服务**

go

```go
// main.go
package main

import (
    "fmt"
    "net/http"
    "os"
)

func main() {
    port := os.Args[1]
    http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
        fmt.Fprintf(w, "response from :%s\n", port)
    })
    http.HandleFunc("/healthz", func(w http.ResponseWriter, r *http.Request) {
        w.WriteHeader(200)
        fmt.Fprintln(w, "ok")
    })
    http.ListenAndServe(":"+port, nil)
}
```

bash

```bash
go run main.go 8081 &
go run main.go 8082 &
go run main.go 8083 &
```

**2. 配 Nginx**

```nginx
# /etc/nginx/conf.d/lb.conf
upstream go_backend {
    least_conn;
    server 127.0.0.1:8081 weight=3 max_fails=2 fail_timeout=10s;
    server 127.0.0.1:8082 weight=2 max_fails=2 fail_timeout=10s;
    server 127.0.0.1:8083 backup;
    keepalive 32;
}

server {
    listen 8080;

    location / {
        proxy_pass http://go_backend;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_next_upstream error timeout http_502 http_503;
    }
}
```

bash

```bash
nginx -t && nginx -s reload
```

**3. 验证**

bash

```bash
# 连续请求 10 次，观察分布
for i in $(seq 1 10); do curl -s http://localhost:8080/; done

# 预期：8081 出现约 3 次，8082 约 2 次（weight 3:2），8083 不出现
```

**4. 验证故障摘除**

bash

```bash
# 杀掉 8081
kill %1

# 再请求，8081 应该在 max_fails 次失败后被摘除，流量走 8082
for i in $(seq 1 10); do curl -s http://localhost:8080/; done
```

### 常见坑

- **没配 `proxy_http_version 1.1` 和 `Connection ""`**：keepalive 不生效。
- **`max_fails=0`**：表示不做失败检查，永远不会摘除。
- **健康检查是被动的**：Nginx 开源版只在请求失败时判断，没有主动探活。要主动探活得用 Nginx Plus 或 OpenResty。
- **`backup` 节点平时不参与**：别误以为它也在轮询。

# 实战：gRPC round_robin + 服务发现（1~2 天）

### 目标

让 Go 的 gRPC 客户端从注册中心拿到多个实例，并轮询调用。

| 概念        | 含义                           |
| :---------- | :----------------------------- |
| Resolver    | 把 target 字符串解析成地址列表 |
| Balancer    | 从地址列表里选一个的策略       |
| pick_first  | 默认策略，只用一个地址         |
| round_robin | 轮询策略                       |
| 服务注册    | 服务启动时把地址写入注册中心   |
| 服务发现    | 调用方从注册中心读地址列表     |
| 健康检查    | 注册中心判断实例是否存活       |

### 实操步骤

**1. 起 Consul**

bash

```bash
docker run -d --name consul -p 8500:8500 consul
# 打开 http://localhost:8500 看 UI
```

**2. 定义 proto**

proto

```proto

package user;
option go_package = "./pb";

service UserService {
    rpc GetUser (GetUserReq) returns (GetUserResp);
}

message GetUserReq { int32 id = 1; }
message GetUserResp { string name = 1; string instance = 2; }
```

bash

```bash
protoc --go_out=. --go-grpc_out=. user.proto
```

**3. 写服务端（注册 + 健康检查）**

go

```go
// user-service/main.go
package main

import (
    "context"
    "fmt"
    "net"
    "os"
    "os/signal"
    "syscall"

    "github.com/hashicorp/consul/api"
    "google.golang.org/grpc"
    "google.golang.org/grpc/health"
    "google.golang.org/grpc/health/grpc_health_v1"
    pb "your-module/pb"
)

type server struct {
    pb.UnimplementedUserServiceServer
    instance string
}

func (s *server) GetUser(ctx context.Context, req *pb.GetUserReq) (*pb.GetUserResp, error) {
    return &pb.GetUserResp{Name: "alice", Instance: s.instance}, nil
}

func main() {
    port := os.Args[1]                 // 9001 / 9002 / 9003
    instanceID := "user-service-" + port

    lis, _ := net.Listen("tcp", ":"+port)
    grpcServer := grpc.NewServer()
    pb.RegisterUserServiceServer(grpcServer, &server{instance: instanceID})

    // 注册健康检查服务
    healthServer := health.NewServer()
    healthServer.SetServingStatus("", grpc_health_v1.HealthCheckResponse_SERVING)
    grpc_health_v1.RegisterHealthServer(grpcServer, healthServer)

    // 注册到 Consul
    consulClient, _ := api.NewClient(api.DefaultConfig())
    consulClient.Agent().ServiceRegister(&api.AgentServiceRegistration{
        ID:      instanceID,
        Name:    "user-service",
        Address: "127.0.0.1",
        Port:    atoi(port),
        Check: &api.AgentServiceCheck{
            GRPC:                           "127.0.0.1:" + port,
            Interval:                       "5s",
            DeregisterCriticalServiceAfter: "30s",
        },
    })

    go grpcServer.Serve(lis)
    fmt.Println("serving on", port)

    // 优雅退出
    quit := make(chan os.Signal, 1)
    signal.Notify(quit, syscall.SIGINT, syscall.SIGTERM)
    <-quit
    consulClient.Agent().ServiceDeregister(instanceID)
    grpcServer.GracefulStop()
}
```

        "consul://127.0.0.1:8500/user-service?healthy=true",
        grpc.WithTransportCredentials(insecure.NewCredentials()),
        grpc.WithDefaultServiceConfig(`{

    }
}

## 实战：优雅退出 + 健康检查接口写法

### 目标

让你的 Go 服务在发布/重启时不给客户端返回 502，并让 LB 正确判断存活。

| 概念         | 含义                               |
| :----------- | :--------------------------------- |
| liveness     | 存活探针，失败就重启               |
| readiness    | 就绪探针，失败就从 LB 摘除但不重启 |
| SIGTERM      | K8s/系统停止进程时发的信号         |
| GracefulStop | gRPC 优雅关闭                      |
| Shutdown     | HTTP 优雅关闭                      |
| 连接排空     | 等已有请求处理完再退出             |
| 注销延迟     | 先注销，等 LB 感知，再退出         |

### 完整代码模板

```go
package main

import (
    "context"
    "errors"
    "log"
    "net/http"
    "os"
    "os/signal"
    "syscall"
    "time"
)

func main() {
    mux := http.NewServeMux()

    // 存活检查：进程活着就 200
    mux.HandleFunc("/healthz", func(w http.ResponseWriter, r *http.Request) {
        w.WriteHeader(http.StatusOK)
        w.Write([]byte("ok"))
    })

    // 就绪检查：依赖都通才 200
    mux.HandleFunc("/readyz", func(w http.ResponseWriter, r *http.Request) {
        if err := checkDependencies(); err != nil {
            w.WriteHeader(http.StatusServiceUnavailable)
            w.Write([]byte("not ready: " + err.Error()))
            return
        }
        w.WriteHeader(http.StatusOK)
        w.Write([]byte("ready"))
    })

    mux.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
        time.Sleep(2 * time.Second) // 模拟慢请求
        w.Write([]byte("done"))
    })

    srv := &http.Server{Addr: ":8080", Handler: mux}

    go func() {
        if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
            log.Fatalf("listen: %v", err)
        }
    }()
    log.Println("server started on :8080")

    // 等信号
    quit := make(chan os.Signal, 1)
    signal.Notify(quit, syscall.SIGINT, syscall.SIGTERM)
    <-quit
    log.Println("shutting down...")

    // 1. 从注册中心注销（如果有 Consul/Etcd）
    // deregisterFromConsul()

    // 2. 等待 LB 感知（通常 3~10 秒，取决于健康检查间隔）
    time.Sleep(5 * time.Second)

    // 3. 优雅关闭，给在途请求 30 秒处理时间
    ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
    defer cancel()
    if err := srv.Shutdown(ctx); err != nil {
        log.Fatal("forced shutdown:", err)
    }
    log.Println("server exited")
}

func checkDependencies() error {
    // 检查 DB、Redis 等
    // if err := db.Ping(); err != nil { return err }
    return nil
}
```

### 关键点

**1. `/healthz` 和 `/readyz` 必须分开**

| 探针      | 失败后果   | 检查内容     |
| :-------- | :--------- | :----------- |
| liveness  | 重启容器   | 进程是否卡死 |
| readiness | 从 LB 摘除 | 依赖是否就绪 |

**2. 退出顺序不能错**

text

```text
收到 SIGTERM
  → 停止接受新连接（但不断已有连接）
  → 从注册中心注销
  → 等 LB 感知（关键！）
  → 等在途请求处理完
  → 退出
```

如果顺序错了（比如直接 `os.Exit`），LB 还没感知你就没了，客户端收到 502。

**3. 等待时间怎么定**

- 大于 LB 健康检查间隔 × 2。
- Nginx 被动检查：等 `fail_timeout` 相关时间。
- Consul 主动检查：等 `Interval` 相关时间。
- 一般 5~10 秒。

**4. K8s 里额外注意**

yaml

```yaml
lifecycle:
  preStop:
    exec:
      command: ["sleep", "10"]   # 给 LB 摘除留时间
terminationGracePeriodSeconds: 60
```

### 验证方式

bash

```bash
# 用一个慢请求 + kill 测试
curl http://localhost:8080/ &   # 慢请求，2 秒
sleep 0.5
kill -TERM <pid>                 # 发 SIGTERM

# 预期：curl 正常返回 "done"，而不是 connection refused
```

### 常见坑

- **直接 `os.Exit(0)`**：在途请求全断。
- **不注销就退出**：LB 还会发流量。
- **`/healthz` 检查了 DB**：DB 抖动导致容器被反复重启，应该只在 `/readyz` 检查。
- **`http.Server.Shutdown` 没设超时**：请求卡住永不退出。
